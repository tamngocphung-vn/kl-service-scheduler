# Decisions and assumptions

Part of the [system design](SYSTEM_DESIGN.md). Decisions are referenced elsewhere by ID (D1–D13, A1–A11), so IDs are never reused or renumbered. New decisions are added at the end of the table.

## Decisions confirmed with the product owner

The brief leaves these open. I put them to the product owner (myself, acting in that role for this assessment) as explicit options with trade-offs. Recorded 2026-10-29.

| # | Decision | Chosen over | Consequence |
|---|---|---|---|
| D1 | The booker is a **service advisor** (dealership staff). Customers and vehicles already exist in the DMS. | Customer self-service; both | No customer sign-up or "my vehicles" flow. Unknown customer or vehicle → 404. Authorisation is by dealership ([Build for the future §7](BUILD_FOR_THE_FUTURE.md#7-security-and-privacy)). |
| D2 | The **system auto-assigns** the technician and bay (see A1). | Optional preferred technician; caller picks both | Simple, deterministic API. A caller-supplied `technicianId` is rejected (400) rather than silently ignored. |
| D3 | Technicians work **whenever the dealership is open**. No shifts, breaks or leave (see A4). | Per-technician shifts | Availability can overstate capacity on days a technician is absent. Listed as [future work](SYSTEM_DESIGN.md#9-future-work). |
| D4 | Scale targets are those of a **dealer group** ([design §1.2](SYSTEM_DESIGN.md#12-non-functional-requirements)). | National platform; unstated | A single SQLite node is acceptable. PostgreSQL is the documented growth path ([Build for the future §1](BUILD_FOR_THE_FUTURE.md#1-scalability)). |
| D5 | Recovery: **RPO 24 h, RTO 4 h**, from nightly backups. | RPO ≤ 1 min (continuous replication) | Simpler operations, but **up to a day of confirmed bookings can be lost** in a disaster. Recommended production target and trigger: [Build for the future §6](BUILD_FOR_THE_FUTURE.md#6-upgrade-triggers). |
| D6 | Appointment records are **kept indefinitely** as service history. | Anonymise after ~7 years; out of scope | History grows without bound. That drives the query fix in [Build for the future §2](BUILD_FOR_THE_FUTURE.md#2-performance), and needs a documented GDPR legitimate-interest basis ([Build for the future §7](BUILD_FOR_THE_FUTURE.md#7-security-and-privacy)). Recommended: 7 years, then anonymise ([Build for the future §6](BUILD_FOR_THE_FUTURE.md#6-upgrade-triggers)). |
| D7 | Appointments can be booked at most **90 days ahead**. | No limit; configurable per dealership | Bounds future-dated data. Implemented as 422 `BEYOND_BOOKING_HORIZON`; the availability endpoint offers no slots past the horizon. The limit is a service option, so per-dealership configuration is a small change. |
| D8 | **Single global deployment** serving all regions (UK, Australia). | Regional deployments | Simplest to run, but **UK/EU and Australian customer data share one database**, which may conflict with data-residency rules ([Build for the future §7](BUILD_FOR_THE_FUTURE.md#7-security-and-privacy)). Recommended: regional deployments, with triggers in [Build for the future §6](BUILD_FOR_THE_FUTURE.md#6-upgrade-triggers). |
| D9 | **API versioning:** the URL carries the major version (`/v1`) and the code mirrors it (`src/routes/v1/`). Releases follow semver, with `package.json` as the single source (served as OpenAPI `info.version`), a git tag `vX.Y.Z` and `CHANGELOG.md`. | Header or media-type versioning; unversioned routes | Additive changes stay in `/v1`. A breaking change adds `src/routes/v2/`, reusing the same services and domain, and runs alongside `/v1` until it is retired. Global schema `$id`s (`Appointment`, `ErrorResponse`) are shared, so a v2 shape needs its own `$id`. |
| D10 | **Non-functional targets** (recorded 2026-10-30): correctness before speed (zero double-bookings), 99.9% availability, booking and availability p95 < 1 s (booking p99 < 2 s), 10 bookings/s at peak with 5× bursts, and **UK/EU GDPR compliance**. | A tighter p95 < 300 ms | The latency budget leaves room for a separately deployed database and future pricing (e.g. holiday surcharges). GDPR turns the D6 retention upgrade, the D8 regional split, authentication, erasure and export into go-live prerequisites ([Build for the future §7](BUILD_FOR_THE_FUTURE.md#7-security-and-privacy)). |
| D11 | **Observability on a managed cloud service** (recorded 2026-10-30). The code emits OpenTelemetry traces, Prometheus metrics and JSON logs; storage, dashboards and alerting are bought. The vendor is chosen at deployment. | Self-hosted Prometheus, log stack and Jaeger | Less to build and run. The work in the code is the OpenTelemetry SDK setup and one span around the booking transaction. Telemetry carries IDs only, and the vendor must store data in-region under a data-processing agreement (GDPR). |
| D12 | **SQLite for the prototype, PostgreSQL for production** (chosen at project start). | PostgreSQL (with Prisma) from day one | SQLite uses the same relational SQL model, and Drizzle keeps the schema and queries portable, so the move is a dialect switch plus migrations. While requirements are still being settled (assumptions A1–A11), a zero-setup database keeps changes quick, and reviewers can run it with `npm install`. Trade-off: the concurrency guarantee doesn't port as-is. SQLite's single write lock becomes per-resource exclusion constraints on PostgreSQL ([Build for the future §1](BUILD_FOR_THE_FUTURE.md#1-scalability)). The move happens when a trigger in [§6](BUILD_FOR_THE_FUTURE.md#6-upgrade-triggers) fires. |
| D13 | **One configuration profile per environment; secrets to AWS Secrets Manager** (recorded 2026-10-30). `config/dev.env`, `config/pre-prod.env` and `config/prod.env` hold each environment's settings, with fake placeholders for any key. Before go-live, credentials such as database accounts move to AWS Secrets Manager. | A single `.env`; secrets in the orchestrator's config | Environments are reproducible and reviewable in git. The code reads only environment variables, so moving secrets to the manager needs no code change ([Build for the future §6](BUILD_FOR_THE_FUTURE.md#6-upgrade-triggers)). |

## Assumptions (the brief leaves these open)

| # | Assumption | Rationale |
|---|---|---|
| A1 | **The system assigns** the technician and bay. The client only chooses dealership, service type, vehicle and time. **Confirmed (D2).** | Matches "check availability of a bay and a qualified technician". Customers rarely choose a specific bay. A `preferredTechnicianId` could be added later. Unknown fields are rejected (400), not silently ignored. |
| A2 | Each **service type has a fixed duration**, and a **technician is qualified per service type** (many-to-many). | Simplest model that makes "qualified" meaningful. |
| A3 | **Every bay can host every service.** | Bay capabilities (lift, alignment rig, EV isolation bay) would mirror technician qualifications; listed as future work. |
| A4 | Each dealership has one daily opening window in its **own IANA timezone**. An appointment must start and finish inside it. Every day is a working day, and every active technician works all opening hours. **Confirmed (D3).** | Real groups span timezones (the seed data includes London and Sydney). Per-weekday hours, holidays and technician shifts or leave are future work. |
| A5 | Times are exchanged as ISO 8601 with an offset and stored as **UTC epoch ms**. Intervals are half-open `[start, end)`, so back-to-back bookings are allowed. | Makes overlap detection unambiguous and testable. |
| A6 | No buffer time between jobs, and a job is never split across technicians or days. | Keeps the prototype simple. A buffer would be a per-service-type setting. |
| A7 | A **vehicle cannot have two overlapping appointments** (at any dealership). | Prevents a car being physically in two places. |
| A8 | Allocation policy is **first-fit in stable ID order**. | Deterministic and easy to test. Load balancing (least-booked technician) is a pluggable improvement. |
| A9 | Customers, vehicles, technicians and bays are **reference data owned by other systems** (CRM/DMS) and are seeded here. | The brief is about booking, not master-data management. |
| A10 | **Authentication and authorisation are out of scope.** The API assumes it sits behind a gateway that authenticates the caller. | The gateway design is in [Quality §7](BUILD_FOR_THE_FUTURE.md#7-security-and-privacy). |
| A11 | Cancellation is in scope (it releases resources). Rescheduling is cancel-then-book. | Needed to show resources being freed. |
